## Development workflow

### 1. Fork + clone

```bash
git clone https://github.com/<your-fork>/Open-Papertrade.git
cd Open-Papertrade
git remote add upstream https://github.com/Open-Papertrade/Open-Papertrade.git
```

### 2. Set up as usual

Follow [Installation](getting-started/installation.md) — venv, deps, `.env`, migrations, both dev servers.

### 3. Branch

```bash
git checkout -b feature/short-description
```

Branch naming:

* `feature/…` — new features
* `fix/…` — bug fixes
* `docs/…` — documentation only
* `refactor/…` — code restructure without behavior change

### 4. Make the change

Keep changes focused. One PR = one concern.

### 5. Test locally

Run the app end-to-end. If your change touches the filings retrieval or QA layer:

```bash
python manage.py evaluate --hybrid --rerank --out my_change.json
# compare vs. a baseline run before your change
```

Numbers speak louder than intuition.

### 6. Commit + push

```bash
git add <files>
git commit -m "Concise summary of what changed and why"
git push origin feature/short-description
```

Commit messages should describe **why**, not what — the diff already shows what.

### 7. Open a PR

* Reference any related issue.
* Include a "how to verify" section — the exact commands to reproduce.
* If the change is UI-facing, include a screenshot or a short screen-cap.
* If the change is retrieval/eval-facing, include before/after eval numbers.

## Code style

* **Python**: PEP 8, type hints where they help, no over-abstraction. Comments only when the "why" is non-obvious.
* **TypeScript**: strict mode, existing formatting conventions (see the rest of `frontend-ui/`), Tailwind for styles.
* **No AI attribution**: keep commit messages and code comments free of "generated by X" tags.

## The design principles to preserve

If you're touching the AI pipeline, keep the design principles intact:

1. **Refusal over hallucination** — every AI feature has an "I don't know" path.
2. **Measure everything** — new retrieval features come with eval numbers.
3. **Provider-agnostic** — don't hard-code a vendor name in reasoning code.
4. **Traceable citations** — new chunk types must preserve `char_start`/`char_end`.
5. **Explainable retrieval** — prefer NumPy-visible logic to framework calls where possible.

## Reporting bugs

Open an issue with:

* What you tried (exact commands).
* What you expected.
* What actually happened (full error, please).
* Your `LLM_PROVIDER` value (**do not paste your API key**).

## Feature ideas

Big-picture ideas live in `IDEA.md` and `readme/FEATURE_IDEAS.md`. If you have a new idea, open a discussion issue before starting to code — saves both sides time.

## Community

Be kind. Assume good faith. Concise, technical feedback is better than long, vague feedback.
